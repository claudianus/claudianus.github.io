에이전트에게 작업을 맡기기 전에 배운 것들

2026. 07. 18. · #ai-agents #작업분해 #병렬워커

작업을 “분해한다”는 말의 함정

“큰 작업을 작게 나눠서 병렬로 처리하면 빠르다” — 이 문장은 맞지만, 절반만 맞다. superliora에 작업 분해를 구현하면서 가장 먼저 배운 건 이것이다. 나누기 쉬운 작업과 병렬화에 적합한 작업은 다르다.

한 파일을 두 워커가 동시에 고치는 상황을 상상해 보자. 두 결과 모두 완벽할 수 있지만, 병합하는 순간 충돌이 난다. 병렬화의 진짜 조건은 작업의 크기가 아니라 작업 간의 독립성이다.

독립성을 만드는 세 가지 방법

실전에서 독립성을 확보한 방법 세 가지를 정리한다.

1. 경계를 먼저 나눈다

작업을 나누기 전에, 수정 대상의 경계를 먼저 나눈다. 모듈, 디렉터리, 인터페이스가 명확하면 워커의 영역이 겹치지 않는다. 경계가 흐릿한 코드베이스에서는 병렬화보다 직렬화가 오히려 빠르다.

2. 계약을 고정한다

병렬 워커 사이의 계약 — 함수 시그니처, 타입, 데이터 형식 — 을 작업 시작 전에 확정한다. 워커가 계약을 가정하게 되면, 나중에 모든 가정을 검증하는 비용이 병렬화로 얻은 시간을 다시 가져간다.

3. 산출물의 형식을 지정한다

“리팩터링해 와”는 산출물이 아니라 지시다. “테스트 통과 + 기존 API 유지 + 변경 파일 목록 포함”이 산출물이다. 산출물 형식이 명확하면 병합 단계에서 판단이 필요 없다.

실패 사례: 완벽한 계획, 무너진 병합

가장 기억에 남는 실패는 이렇다. planner 세션이 6개의 완벽하게 분해된 작업을 만들었다. 워커 6개가 각자의 작업을 훌륭히 완수했다. 그런데 병합해 보니 6개의 결과가 각각 다른 유틸리티 함수를 새로 정의하고 있었다. 각자의 영역 안에서는 합리적인 결정이었지만, 시스템 전체에서는 중복이었다.

이 실패에서 나온 원칙: 워커의 자유도는 시스템 차원의 일관성이 보장되는 범위 안에서만 허용한다. 공용 유틸리티, 네이밍 규칙, 스타일 결정은 계약에 포함시키고, 워커는 그 안에서만 자유롭다.

병렬화를 포기해야 할 때

마지막으로, 병렬화가 정답이 아닌 경우도 있다.

  1. 작업 간 의존성이 파악되지 않을 때 — 충돌 비용이 병렬 이득보다 크다
  2. 하나의 컨텍스트가 필요한 작업일 때 — 컨텍스트를 쪼개면 각 조각이 모두 불완전해진다
  3. 디버깅이 목적일 때 — 직렬 실행은 원인 추적이 쉽다

엔진 설계에서 배운 교훈은 이것이다. 병렬 워커는 속도의 도구가 아니라 독립성의 증명 도구다. 작업을 병렬로 나눌 수 없다면, 그 작업은 아직 제대로 이해되지 않았다는 신호다.
