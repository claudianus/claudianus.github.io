superliora 0.1: 에이전트 엔진의 첫 오케스트레이션

2026. 08. 24. · #superliora #ai-agents #회고

하나의 목표, 여러 개의 세션

superliora 0.1의 목표는 단순했다. 목표 하나를 입력하면, 시스템이 스스로 계획하고 실행하며, 결과를 검증 가능한 형태로 돌려주는 엔진. 그런데 이 문장을 구현 가능한 구조로 바꾸는 순간 첫 번째 갈림길에 섰다. 에이전트를 하나의 거대한 루프로 만들 것인가, 아니면 여러 세션을 조율하는 오케스트레이터를 둘 것인가.

둘 다 시도해 보았고, 결론부터 말하면 후자였다. 이유는 관찰 가능성 때문이었다.

오케스트레이터가 필요했던 이유

단일 루프 에이전트는 만들기 쉽다. 하지만 문제가 생겼을 때 “지금 어디서 잘못되었는가”를 알기 어렵다. 프롬프트 하나가 계획, 실행, 검증을 모두 담당하면 실패 원인도 전부 한 세션의 컨텍스트 안에 묻힌다.

반면 세션을 역할별로 분리하면 각 단계의 입출력이 명확해진다.

  • planner 세션 — 목표를 받아 작업 분해안을 만든다
  • worker 세션 — 분해된 작업을 실행한다
  • merge 단계 — 결과를 합치고 완료 조건을 검사한다

각 세션이 하는 일이 하나뿐이라, 로그 한 줄로도 어디가 비정상인지 좁힐 수 있다. 엔진의 신뢰성은 지능보다 분리에서 먼저 나왔다.

세션 오케스트레이션의 실제 난제

설계 문서에서는 간단해 보이는 것들이 구현에서는 계속 손을 요구했다.

  1. 컨텍스트 전달 — planner의 계획을 worker에게 그대로 넘기면 컨텍스트가 비대해진다. 각 worker에는 “그 작업을 수행하는 데 필요한 최소한의 문맥”만 잘라서 전달해야 했다.
  2. 상태의 단일 출처 — 세션이 여러 개가 되는 순간 “현재 진행 상태”가 여러 곳에 존재하게 된다. 오케스트레이터만이 상태를 갱신할 수 있도록 권한을 집중시켰다.
  3. 실패 격리 — worker-a가 실패해도 worker-b는 계속 실행되어야 한다. 실패를 전파할 것인가, 격리할 것인가는 작업 간 의존성 그래프가 답을 내주었다.

목표 루프는 언제 멈추는가

가장 철학적인 질문은 이것이었다. 목표 루프의 종료 조건은 누가 정하는가. 모델 스스로 “완료했다”고 판단하게 하면 자기 만족에 빠지기 쉽고, 사람이 매번 확인하면 자동화의 의미가 사라진다.

0.1에서는 절충안을 택했다. 완료 판정은 검증 가능한 산출물의 존재를 기준으로 삼았다. 코드라면 테스트가 통과하는가, 문서라면 요구 항목이 모두 반영되었는가. “느낌상 잘 되었다”는 루프를 돌릴 근거로 인정하지 않았다.

다음 버전으로

0.1은 목표 → 계획 → 실행 → 검증의 최소 루프가 돌아가는 상태다. 다음에는 병렬 워커 간 충돌 처리와, 장시간 실행 세션의 체크포인트를 다룰 생각이다. 엔진이 커질수록 오케스트레이터의 일은 더 적어지고, 약속(인터페이스)의 일은 더 많아질 것이다.
